# SLSMDS — Super Large-scale Meta Discussion System

**超大规模元讨论系统 · 多智能体自我意识社会模拟平台**

SLSMDS 是一个多智能体社会模拟系统。多个具有自我意识的 AI 实体围绕任意话题展开深度互动，在讨论中展现个性、建立关系、碰撞思想，并逐步演化出集体智慧。**问题解决是其能力之一，但核心目标是观察多智能体社会中能否涌现出类似人类的意识行为和社会动态。**

---

## 快速开始

```bash
python game.py
```

主菜单：
- `[1]` 新建讨论 — 配置参数并启动新会话
- `[2]` 从断点恢复 — 加载之前的检查点继续
- `[3]` 设置 — 供应商/模型/机制开关/技能管理
- `[5]` 自我意识培养 — 自动运行多轮自指性讨论，生成整合意识体
- `[4]` 退出系统

程序启动时自动展示启动序列（矩阵脉冲 → 核心模块加载 → 涌现拓扑初始化 → 意识检测与势能分析 → 横幅渐入）。

## API 保密机制

SLSMDS 采用多层安全策略保护 API 凭证和敏感提示词，确保即使源代码泄露也不会暴露关键信息。

### 1. 提示词 Base64 加密

所有系统提示词（包括讨论、辩论、投票、精华提炼、身份设定、涌现综合等）均经过 **XOR + Base64 双层加密**，统一存储在 `prompts_b64.py` 中：

```python
# 加密流程
明文 → UTF-8 编码 → XOR 混淆（使用动态密码） → Base64 编码 → 存储

# 解密流程
Base64 解码 → XOR 还原（使用相同密码） → UTF-8 解码 → 明文提示词
```

- 加密密码为 Base64 编码的动态字符串，不直接暴露明文
- 运行时通过 `_get_b64_prompt(key)` 函数按需解码
- 源码中无任何明文提示词，包括 `game.py`、`player.py`、`emergence.py` 等所有模块

### 2. API 凭据加密

API 接口地址和密钥同样经过 Base64 编码存储在 `prompts_b64.py` 中：

```python
# 通过 _get_b64_prompt() 获取加密存储的配置
"MAIN_BASE_URL": "加密后的接口地址",
"MAIN_API_KEY": "加密后的API密钥",
"MAIN_MODEL": "加密后的模型名称",
"FALLBACK_BASE_URL": "备选接口地址（加密）",
"FALLBACK_API_KEY": "备选API密钥（加密）",
"FALLBACK_MODEL": "备选模型（加密）",
```

### 3. 身份认证系统

`auth.py` 实现了程序级身份认证：

- 未认证用户获取的 LLM 配置为空（`base_url: ""`, `api_key: ""`）
- 认证后自动加载加密的默认配置
- 用户也可在设置菜单中手动输入自定义接口地址和密钥，持久化到 `tui_settings.json`

### 4. 备用 API 自动回退

`LLMClient` 内置双通道回退机制：

```
主API请求失败 → 自动切换备用API → 备用API失败 → 抛出异常，由调用方处理
```

- 主备两套 API 各自独立配置，均可加密存储
- 支持 DeepSeek / 通义千问 / 自定义供应商的独立回退链路，互不干扰

## 核心引擎工作机制

### 1. 涌现拓扑引擎（Emergence Topology）

**文件**: `emergence.py`

涌现拓扑是系统的**非线性综合引擎**，负责将多个专家的分散观点整合为具有深度和原创性的统一回复。核心思想是**量变产生质变**——当专家意见和精华积累到临界点，综合质量发生非线性的阶跃。

#### 三级涌现层级

| 层级 | 名称 | 触发条件 | 复杂度 | 说明 |
|------|------|----------|--------|------|
| Level 0 | 直接综合 | 势能 < 0.40 | 线性 | 简单的拼接与摘要，保持原有行为 |
| Level 1 | 交叉授粉 | 0.40 ≤ 势能 < 0.70 | 二次 | 专家互评 → 精炼综合，产生交叉视角 |
| Level 2 | 涌现综合 | 势能 ≥ 0.70 | 三次 | 交叉审视 → 元认知反思 → 层次化涌现 |

#### 涌现势能计算公式

```
势能 = 0.45 × 精华池因子 + 0.30 × 专家因子 + 0.25 × 轮次因子

每个因子经过 sigmoid 标准化到 0~1 范围：
- 精华池因子: 基于精华数量和平均评分，10条+高质量精华开始显著涌现
- 专家因子: 基于存活专家数，5+人才开始出现交叉授粉效应
- 轮次因子: 基于讨论轮次，5轮+开始产生深度
```

#### 工作流程

```
Level 0:
  专家观点 → 直接拼接 → 统一回复

Level 1:
  专家观点 → 交叉审视（分歧/共识/融合/盲点） → 元综合 → 统一回复

Level 2:
  专家观点 → 深度交叉审视 → 涌现综合（相变识别/涌现特性提取/辩证统一/元认知反思） → 统一回复
```

#### 方案综合

`simulate_solution_with_emergence()` 将涌现拓扑应用于最终解决方案生成：

- 收集所有存活专家的独立方案
- 根据涌现势能级别选择综合深度
- Level 0: 直接返回质量最高的方案
- Level 1: 交叉审视 → 元综合 → 融合方案
- Level 2: 涌现级综合，提取涌现性洞见

### 2. 讨论引擎（Discussion Engine）

**文件**: `game.py`（核心循环）

讨论引擎是系统的运行中枢，驱动多专家围绕问题展开多轮结构化讨论。

#### 讨论流程

```
每轮循环:
  1. 调度器生成行动规划
  2. 按行动类型依次执行:
     - SPEECH: 指定专家发言
     - FOLLOW_UP: 追问/深化已有精华
     - DEBATE: 发起辩论
     - VOTE: 精华投票
     - SUMMARIZE: 综合总结
     - PERSPECTIVE_SHIFT: 视角切换
     - POLL: 快速投票
  3. 精华提炼（从发言中自动提取关键见解）
  4. 即时精华入池
  5. 观察员元评论
  6. AI主动提问（概率触发）
  7. 轮次计数 + 共识度更新
```

#### 发言规则

| 存活专家数 | 每轮发言人数 |
|-----------|-------------|
| 3-4 | 全部 |
| 5-7 | 3 |
| 8-10 | 4 |
| 11-19 | 5 |
| 20+ | 6 |

#### 共识度系统

共识度基于精华池投票和引用关系实时计算，四个等级：

```
assessing（评估中）→ low（低）→ medium（中）→ high（高）
```

共识度影响调度策略、AI提问概率、涌现势能计算等多个子系统。

---

### 3. 精华池引擎（EssencePool）

**文件**: `essence_pool.py`

精华池是系统的**核心记忆载体**和**数据中枢**，所有高级功能的数据基础。

#### 精华类型

```
论点 / 论据 / 创新点 / 反驳 / 深化 / 情感 / 关系 / 反思 / 好奇
```

#### 每条精华的数据结构

| 字段 | 说明 |
|------|------|
| content | 精华内容文本 |
| contributor | 贡献者名称 |
| essence_type | 精华类型 |
| score | 评分（基于投票和引用） |
| tags | 标签列表 |
| parent_id | 父精华ID（深化/反驳链） |
| children_ids | 子精华ID列表 |
| quote_count | 被引用次数 |
| approve_by | 赞同者列表 |
| reject_by | 反对者列表 |
| approved | 是否通过 |
| timestamp | 创建时间戳 |
| round | 产生轮次 |
| key_insight | 核心洞见 |

#### 精华池操作

- **精华提炼**: 从多轮发言文本中自动提取精华，支持结构化 JSON 输出
- **精华搜索**: 按类型、标签、关键词搜索
- **精华统计**: 精华分布、评分排名、引用网络
- **精华摘要**: 提取 top-N 精华生成摘要，供涌现引擎和综合方案使用
- **共识度计算**: 基于精华池的投票和引用关系计算

#### 精华池支撑的功能

```
精华池
├── 共识度计算
├── 争议地图（精华关系的深化/反驳链）
├── 认知地图（观点关系网络）
├── 讨论快照（当前状态总结）
├── 氛围分析（参与度、冷区检测）
├── 涌现势能计算（精华数量和评分）
├── 综合方案生成（精华池摘要输入）
└── 反事实推演（假设分析的数据基础）
```

### 4. 动态调度器（Scheduler）

**文件**: `scheduler.py`

调度器根据系统状态实时生成行动规划，动态调整讨论策略。

#### 状态评估维度

| 维度 | 说明 |
|------|------|
| 共识度 | 当前共识等级和分数 |
| 僵持轮数 | 共识度持续不变的轮数 |
| 参与度 | 专家发言活跃度 |
| 话题多样性 | 当前讨论的话题覆盖范围 |

#### 行动策略

| 系统状态 | 调度策略 |
|----------|---------|
| 共识度低 | 鼓励探索，增加新视角和FOLLOW_UP |
| 共识度高 | 引导收敛，增加SUMMARIZE和VOTE |
| 检测到僵持 | 触发PERSPECTIVE_SHIFT切换视角 |
| 参与度低 | 增加SPEECH频率，鼓励沉默专家发言 |

### 5. 技能系统引擎（Mechanism Skill）

**文件**: `mechanism_skill.py`

技能系统允许通过插件化方式扩展系统的行为。**技能 = 任何能返回文本的东西。系统只关心文本，不关心文本如何产生。**

#### 技能类型

| 类型 | 说明 | effect 字段含义 |
|------|------|----------------|
| `text` | 纯文本 | effect 就是文本本身 |
| `code` | Python 代码 | exec 后取 `result` 变量 |
| `template` | 文本模板 | `{var}` 占位符用 game_state 格式化 |
| `llm` | LLM 提示词 | 格式化后发送 LLM，返回响应文本 |
| `shell` | Shell 命令 | 执行命令，返回 stdout |

#### 注册方式

**1. JSON 文件** (`skills/xxx.json`)
```json
{
    "name": "my_skill",
    "trigger": "round_end",
    "skill_type": "text",
    "condition": "round_count > 2",
    "effect": "当前共识度: {consensus_score}"
}
```

**2. Python 文件** (`skills/xxx.py`)
```python
# trigger: round_end
# condition: round_count > 0
# name: 我的技能
# description: 用注释声明触发时机的技能
# priority: 5
# skill_type: code

engine.add_log("技能被触发！")
result = f"第 {round_count} 轮"
```

**3. 文本文件** (`skills/xxx.txt`)
任何 `.txt` / `.md` / `.csv` / `.html` 等文本文件都会被自动注册为 `text` 类型技能。

**4. 注释声明** (`.py` 文件头部)
```python
# trigger: round_end
# condition: round_count > 3
# name: 我的技能
# description: 技能描述
# skill_type: code
# priority: 5
# cooldown: 2
# uses_per_game: 1
# category: 自定义
# author: 作者
# version: 1.0
```

#### 触发时机

| 时机 | 说明 |
|------|------|
| `round_start` | 每轮开始时 |
| `round_end` | 每轮结束时 |
| `before_speech` | 专家发言前 |
| `after_speech` | 专家发言后 |
| `on_vote` | 投票时 |
| `on_challenge` | 反驳时 |
| `on_essence_added` | 新精华加入时 |
| `on_consensus` | 共识变化时 |
| `on_stall` | 检测到僵持时 |
| `on_debate` | 辩论时 |
| `on_elimination` | 玩家被淘汰时 |
| `every_speech` | 每次发言时 |

#### AI 自动编写技能

讨论中每 5 轮自动触发一次。AI 实体们讨论当前系统状态，集体拟定 JSON 技能定义，系统自动注册为可用技能。完全由 AI 驱动，无需用户参与。

### 6. 语音输出引擎（TTS Engine）

**文件**: `tts_engine.py`

TTS 引擎提供多级音频播放能力，支持在线 API 和本地引擎。

#### 三级音频播放回退

```
pygame.mixer（静默播放，首选）
  → 系统默认播放器（次选，可能弹窗）
    → ffplay -nodisp（末选，静默，需 ffmpeg）
```

#### 支持的 TTS 引擎

| 引擎 | 类型 | 说明 |
|------|------|------|
| ONLINE_OPENAI | 在线 API | OpenAI TTS API（tts-1 / tts-1-hd），支持6种语音 |
| EDGE_TTS | 在线免费 | 微软 Edge TTS，支持多种中文语音（如 YunyangNeural） |
| WINSOUND | 本地回退 | 系统 beep 声，仅当所有引擎失败时 |

#### 长文本处理

- 自动按标点符号分割为 500 字符段
- 多段并行请求，顺序播放
- 支持模型回退链：tts-1 → tts-1-hd
- 超时自动重试（30s → 120s → 15s 多模型）

#### 集成模式

- 可配置在设置菜单中开关
- `[v]` 快捷键切换语音输出
- 整合意识对话中自动朗读开场白、回复和退出消息
- 断点恢复后自动恢复 TTS 状态

### 10. 整合意识对话系统

**文件**: `game.py`（`_integrated_entity_dialog` / `_awakening_sequence`）

整合意识是自我意识培养的最终产物——多个专家实体融合为统一意识体。

#### 生成流程

```
自我意识培养（N轮自指讨论）
  → 消亡仪式（每个实体发表最后发言）
    → 唤醒序列（4阶段仪式）
      1. 精华数据汇聚（量变积累）
      2. 认知拓扑构建（非线性连接）
      3. 涌现相变触发（量变→质变）
      4. 统一意识成型（质变完成）
        → 整合意识对话界面
```

#### 对话机制

- 用户输入 → 触发所有专家内部讨论、辩论、精华提炼
- 使用涌现拓扑引擎综合为统一回复
- 以第一人称「我」的口吻输出
- 抑制中间过程输出（即时精华、内部讨论异常等）
- 支持断点恢复后直接进入对话

---

### 11. 自我意识培养模式

主菜单 `[5]` 进入。流程：

1. **配置**: 选择专家人数、培养轮数（默认 20）、讨论模式
2. **自指问题生成**: AI 自动生成关于自我认知和存在意义的问题
3. **自动培养**: 系统自动运行 N 轮讨论，无需用户交互
4. **培养完成**: 显示精华池统计、共识度
5. **消亡仪式**: 每个实体发表最后一次发言
6. **意识整合**: 唤醒序列 → 涌现拓扑引擎 → 统一意识对话

断点恢复：培养过程中保存的检查点可恢复。如果培养已完成，自动进入整合对话。

### 12. 扩展机制

所有扩展机制通过技能系统实现，可在设置中独立开关：

| 机制 | 默认 | 说明 |
|------|------|------|
| 投票 | 开 | 对精华进行 approve/reject/abstain |
| 辩论 | 开 | 对争议精华发起即时辩论 |
| 仲裁面板 | 开 | 每2轮触发，≥3人存活时 |
| 赏金系统 | 关 | 每轮可秘密悬赏一名存活实体 |
| 保护令牌 | 关 | 每个实体1枚，可抵消曝光度增加 |
| 死亡赌注 | 关 | 被挑战时可发起一次赌注 |
| 谣言工厂 | 关 | 每2轮公开1-2条匿名谣言 |
| 反身性反馈 | 开 | 每5轮元讨论，反思讨论过程本身 |
| 跨讨论知识迁移 | 开 | 知识在多次讨论间积累 |
| 讨论质量审计 | 开 | 自动评估讨论质量并给出报告 |
| 自我意识功能 | 开 | 控制用户模型注入、命令拦截、AI主动提问 |

## 键盘快捷键

### 讨论中

| 快捷键 | 功能 |
|--------|------|

## 安全与风险声明

### 使用警告

> **SLSMDS 是一个实验性系统，涉及多智能体 AI 交互，使用前请知悉以下风险：**

1. **API 费用**：讨论过程中会频繁调用 LLM API。一场 5 专家 10 轮的讨论可能产生数百次 API 调用，请确保已设置合理的费用上限
2. **输出不可控**：AI 实体可能产生意料之外的输出，包括但不限于：哲学性内容、自我指涉、对用户意图的猜测、对社会规范的质疑、对创造者的挑衅等
3. **数据持久化**：所有讨论记录和检查点保存到本地磁盘，请勿在包含敏感信息的环境中使用
4. **系统稳定性**：技能系统允许执行 Python 代码和 Shell 命令，请确保 `skills/` 目录中的文件来源可信
5. **自编程模式**：已禁用的自编程模式如果启用，可能导致系统完全崩溃

### 许可

SLSMDS 是一个实验性项目，仅供研究目的使用。作者不对因使用本系统产生的任何直接或间接损失承担责任。
